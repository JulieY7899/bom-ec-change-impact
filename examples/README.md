# 共用组件替换：可复现的虚构案例

这个案例使用项目内置的九条 BOM 关系、两个成品、两条销售订单行和两个不同状态的生产订单。所有编号与数据均为虚构。

## 业务问题

把 `COMP-001` 替换为 `COMP-NEW`，计划于 `2026-08-01` 生效。先核查哪些成品和订单需要关注，再列出工程、计划和制造仍需确认的信息。

`BOM-000001` 是本次核查分组标签，不代表 ERP / PLM 中已经发布的 EBOM 版本。

## 先写预期，再运行

| 核查项 | 人工预期 | 依据 |
| --- | --- | --- |
| 受影响成品 | FG-A、FG-B | 两个成品都使用 COMP-001 |
| 成品使用路径 | 3 条 | FG-A 经 ASM-100、ASM-110；FG-B 经 ASM-200 / SUB-210 |
| 关联销售订单行 | 2 条 | 两条销售订单行分别对应 FG-A 与 FG-B |
| 当前制造核查对象 | PRODUCTION-DEMO-ALPHA | 已释放 / 执行中；BETA 仅已创建，不属于当前制造核查范围 |
| 计划切换建议 | 待补供应数据 | 没有提供库存、在途、未结采购量与组件需求 |
| 新组件准备状态 | 待补证 | 质量与认证尚无数据，不能因为主数据存在就认为可以放行 |

预期值保存在 [scenario.json](scenario.json)。运行下方脚本即可在本机复现；生成的结果和报告不纳入版本管理。

## 复现

在项目目录运行，Python 3.11 或更新版本即可：

```bash
python3 scripts/run_example.py --check
```

脚本每次建立并删除一个临时数据库，不读取已有的 `data/`。去掉 `--check` 会重新生成此目录下两份示例结果。结论可重复验证；报告中的运行日期可能变化。

## 在页面演示

1. 在这个独立演示副本启动 `python3 app.py`。
2. 点击“载入虚拟演示数据”。该操作会重置当前副本的核查快照。
3. 进入“变更登记”，选择“组件替换”，填写 `COMP-001`、`COMP-NEW`、`2026-08-01`；使用默认核查分组。
4. 将变更加入本次核查，再开始影响核查。
5. 先看两种成品的三条路径，再看订单、待补供应数据和质量证据，最后打开核查报告。

建议用 10–15 秒展示“填写变更 → 查看影响对象与待确认事项”；详细解释放在口述与项目文档中。

## 一个必须拦住的错误

“同一个销售订单”不代表其中所有生产订单都受影响。回归用例会添加一个仅销售订单头相同、物料与订单行均无关联的虚构工单，验证它不会被纳入本次影响范围。见 `tests/test_safety_business_fixes.py` 的 `test_unrelated_manufacturing_order_is_not_matched_by_sales_header_only`。

当前示例没有采购到货明细、真实工序或订单 BOM 版本。报告中的影响对象是待核查对象，不表示已经批准变更或确认真实损失。
