# 关键设计决策

[返回项目首页](../README.md) · [业务规则](business-rules.md) · [验证记录](evaluation.md)

本页记录影响当前行为的选择、原因及代价。完整的 EBOM / Order BOM 版本模型仍属于后续设计。

## D1｜用规则与图遍历计算影响范围

**问题：** 工程变更会跨越多层物料关系与订单。核查人员需要知道一条结论来自哪条关系、哪份记录。

**决定：** 让代码执行关系追溯、日期筛选、订单关联和数量计算，并在结果中保留来源。当前版本关闭外部模型调用。

**代价：** 规则需要明确建模，输入字段与业务口径需要维护。用户不能依靠自然语言自动补全所有业务条件。

**验证：** 使用虚构的已知结构和订单建立预期结果，再检查路径、关联对象及来源记录。模型生成解释若在后续恢复，需要独立的数据共享设计和输出评估。

## D2｜证据不足时保留待确认事项

**问题：** BOM 路径可能含替代组、来源版本不明、用量缺失或截断。如果仅把能计算的部分相加，结果容易被误当成完整需求。

**决定：** 单位成品差量只有在相关路径证据完整时才输出合计；不完整时列出复核原因。供应情景缺失时，不给出确定的切换结论。

**代价：** 用户需要补数据或人工确认，能够直接输出的数字减少。这是对原型适用范围的明确约束。

**验证：** 测试包含旧用量冲突、替代组、部分路径不可计算、数值溢出和缺失供应数据。

## D3｜区分日期比较与版本迁移

**问题：** 按日期筛选到不同路径，并不能证明已有订单应该迁移到一个新的工程版本。两者依赖的数据和决策条件不同。

**决定：** 当前只比较同一导入快照在两个日期下的有效路径，明确标注这个范围。EBOM、Order BOM 引用与 EC 生效性作为独立的后续建模工作。

**代价：** 当前工具不能自动迁移订单版本，也不能模拟完整的版本差异与配置变化。

**验证：** 测试检查日期前后的路径变化，包括节点相同但来源行不同的情况；不把这些测试写成“版本迁移已验证”。

## D4｜收紧订单关联，并隔离本次核查结果

**问题：** 一个销售订单抬头可能包含多条不同产品行；同一 BOM 标签也可能被多次核查。扩大关联或混入历史结果，会误导当前影响范围。

**决定：** 生产订单依据涉及成品或准确的销售订单行匹配，不能只凭相同销售订单抬头扩入。汇总同时限定 BOM 标签与当前 `draft_id`。

**代价：** 仍需要进一步建模订单配置、独立版本和实际执行状态；候选关联不等于已经证明实物受影响。

**验证：** 构造“同一销售订单下的无关生产订单”以及“同一 BOM 标签的不同核查批次”反例，验证它们不被混入当前结果。

## D5｜让建议与实际业务执行保持清晰边界

**问题：** 变更可能涉及已采购、已到货、已投产物料，需要多个业务角色判断责任、成本与时间窗口。

**决定：** 输出候选影响、建议、证据和待办，保存用户提供的处置信息。审批与实际执行由工具外的业务流程承担。

**代价：** 当前报告之后仍有人工工作；系统没有企业级权限、签署与审批执行能力。

**验证：** 检查报告和处置记录是否保留状态、范围与责任信息，并明确提示候选建议需要确认。ERP、PLM、MES 回写不在当前实现范围。

## D6｜保留轻量本地运行，准确说明隐私边界

**问题：** 公开作品需要容易复现，也需要防止将业务数据通过可选模型调用外发。“本地运行”本身并不足以说明数据边界。

**决定：** 核心应用使用 Python 标准库与 SQLite；本版禁用模型调用，限定本机监听并检查浏览器请求来源。公开演示只使用合成数据。

**代价：** 本地数据库仍保存部分业务编号，应用未提供静态加密。多文件导入还没有整个快照的原子回滚；本地运行也不等于具备生产环境的安全和运维能力。

**验证：** 本地 HTTP 测试检查模型接口禁用、外部 Host / Origin 拒绝及报告导出。完整运行环境与已验证范围见[验证记录](evaluation.md)。
